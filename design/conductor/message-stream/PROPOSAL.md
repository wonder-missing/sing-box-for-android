# Conductor 消息流展示优化建议

- 性质：提案，不是最终 SPEC
- 日期：2026-11-18
- 范围：消息列表里的思考窗、工具行、回复与过程链的间距、行内代码、每条 assistant 回复的用量，以及列表底部已有的全局工具栏
- 非目标：不改输入栏既有布局与其中的当前上下文用量；不新增图标或控件套路；不改变工具执行、数据语义和现有滚动行为；不把本提案写成全状态规范

本文只记录已经确认的展示意图，以及一些可作起点的量值。实现时请结合现有 UI 的真实状态做必要适配。尺寸、token 和交互细节不是硬性全量覆盖，建议按「请结合现有实现验证」来处理。下列已确认意图请尽量保留；若适配会明显改动这些意图，请先标出冲突，而不是默默改掉。

现有实现里，思考小窗（约两行、内部上滚）、工具行、回合结束时的 usage Notice，以及列表底部的 `ConversationActions`（省略号菜单）已经存在。本提案是在此基础上的展示优化，不是从零设计。落点可考虑从 `ConductorScreen.kt` 的 `ReasoningItem`、`ToolItem`、assistant 正文与 `markdownAnnotated`，以及 `ConversationActions`、`ConductorViewModel` 里回合结束后的 usage Notice 入手，具体文件请自行确认。

## 1. 思考小窗

建议去掉标题栏里的 `Thought` / `Thinking` 以及 `Show` / `Hide`。收起态只保留一个固定高度的两行文本小窗：

- 外部高度固定为恰好两行正文，不随内容把父级撑高。
- 流式输出时在小窗内部滚动，始终看到最新内容；外部高度不变。
- 结束后停在最后两行，不要改成摘要，也不要另起标题。

整块收起态小窗建议都可以点，在原位置展开全文（不要另开一页或对话框）。展开后，全文右上角提供 `Collapse`；点收起后回到两行小窗，收起态不再出现标题或按钮。若收起时仍在流式输出，小窗恢复内部滚动；若已结束，则停留在最后两行。收起时建议尽量保持列表视口锚定在同一窗口，避免整页跳动。

展开、流式加载、结束、再收起是同一套交互，请结合现有实现验证它与文本选择不冲突；不必为此再加一套控件。展开后的自动滚动若会影响用户正在阅读，可作为实现时的校验点处理，不是本提案新加的硬性要求。

## 2. 工具行

建议去掉重复的提示文案 `Tap Details to view the tool output.`，也不再在右侧放 `Details` / `Hide details` 文字。右侧只保留 chevron；整个标题行点击即可展开或收起。详情里仍放完整参数与输出，现有工具行为请保持，不要新造分组。

状态标记建议固定在工具名左侧一个不随状态改变宽度的槽位（可考虑约 16dp，请按现有密度验证），避免名称左右跳动：

- 运行中：小 spinner
- 成功：小对勾
- 失败：小红点（不要用红叉）

状态标记与右侧 chevron 建议与工具名做视觉上的光学垂直居中（对准字身 / x-height，而不是把下划线或 descender 算进包围盒）。现有实现里可能还有 `cancelled` 等状态，请自行选择不破坏语义的呈现，不必为本提案另写一套规范。

失败时不能只靠颜色：折叠态可考虑保留一句简短、可读的失败说明（例如 `Failed · …`），完整错误放在展开详情里，并给屏幕阅读器可用的非颜色标签。

参数：若确实有参数，可在标题下用较淡、紧凑的一行预览；没有参数就不要留空行，也不要写 `No arguments` 之类说明。完整数据只放详情。

## 3. 最终回复的间距

过程链内部的间距，与过程链结束后到最终回复之间的间距，建议拉开一档。可先用现有列表常用的 12dp 作为过程内部起点、24dp 作为回复前起点，这只是起始值，请对照当前设计（例如列表项间距）验证，不是硬性规定。不要加 `Answer` 标题，也不要给回复新做一张卡片。

## 4. 行内代码

这是这次最希望改进的点。正文里的行内代码建议用更弱、更中性的背景，不要描边，很小的圆角和左右内边距；等宽字体的视觉大小靠近正文，不要把行高撑高。

较长的标识符（如工具名）建议优先整词换行；只有当单个标识比一行还宽时，再允许在词内折行。不要出现横向溢出或裁切。复制时仍是原来的文本，不要改内容。

现有实现是 `AnnotatedString` 的背景色，若圆角和内边距不容易直接套上，请结合现有实现选择可行做法。除这里写到的行内代码表现外，不要顺手重做整套 Markdown。

## 5. 每条回复的用量

建议把用量放到每条 assistant 回复下面，做成一行偏淡的紧凑页脚，而不是标题、进度条或单独一块面板。常规宽度下请尽量保持一行。下面的格式只是展示示例，不是真实数据：

`In 12.8k · Out 3.3k · Cache 10.1k`

点击这一行，可考虑沿用现有的就地展开详情方式，把其余已有字段放进去。若当前数据里已有 miss、context 一类信息，请保留在详情中，不要静默丢掉。不要新造用量百分比展示。Cache 与 Input 在含义上可能重叠，不要把它们再加总成一个更大的数。

系统大字体或较窄宽度时，这一行不应被裁切；请自行适配，但不要因此做成一块很大的面板。

目前用量是在回合结束后追加一条 `usage` Notice。建议改到每条 assistant 回复的页脚；若现有数据是回合级而不是逐条级，请结合现有实现验证如何挂载，不要为此编造拆分规则。输入栏里已有的当前上下文用量（`used/limit`）请不要改，也不要在消息流里再做一条重复的 Context 进度条。

## 6. 列表底部的全局工具栏

消息列表底部现有一条会话级工具栏（目前只是左侧省略号菜单，例如导出 transcript / API trace）。请保留它：这是全局的消息流菜单，不是某条回复的用量操作，也不是加载动画。不要新造吸顶或固定定位，不要额外加按钮，现有滚动行为保持即可。它应继续与每条回复的用量页脚分开，不要把省略号复制到每条回复下面。

本提案不展开它的外观细节。

## 建议核对（非穷尽）

实现时可顺便看一看这些情况是否成立，不必当成全量验收清单：

- 工具：运行中、成功、失败；无参数、有参数；展开与收起
- 思考窗：流式两行滚动、结束后最后两行、展开全文再收起
- 较长的行内代码标识能整词折行，且不横向溢出
- 多条回复各自有用量页脚
- 较窄宽度或系统大字体时，用量行和工具名不被裁切

未列出的状态由实现方识别约束并适配布局。这不是「可以忽略已确认意图」；只是本提案没有、也不打算穷尽所有运行时状态。
